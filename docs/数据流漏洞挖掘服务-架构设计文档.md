## 1. 产品定位与价值

### 1.1 一句话描述

**本服务是一个"AI 驱动的代码安全审查员"**：给定一个 C/C++ 程序和一个入口函数，它能自动追踪外部输入数据在程序中的完整传播路径，判断是否存在缓冲溢出、注入攻击、未授权访问等安全漏洞。

### 1.2 解决什么问题

| 传统方式 | 本服务方案 |
|----------|-----------|
| 安全专家人工阅读代码，逐行分析 | AI 自动完成，专家只需复核结果 |
| 分析单个函数需要数小时 | 分析一个调用链（含子函数）分钟级完成 |
| 跨函数调用链追踪容易遗漏 | 自动递归追踪到调用链末端 |
| 结果以文档形式散落各处 | 结构化输出，存入数据库，一键检索 |

### 1.3 典型应用场景

- **固件安全审计**：分析嵌入式设备固件中的网络数据包处理逻辑
- **开源组件评估**：扫描第三方开源库是否存在已知模式的安全漏洞
- **CI/CD 安全门禁**：在代码合入前自动检测新引入的安全风险

## 2. 核心概念通俗解释

### 2.1 什么是"污点数据"

在安全领域，我们把所有**来自外部的、不可信的数据**称为"污点数据"（Tainted Data）。例如：

- 用户通过网页表单提交的内容
- 网络数据包的载荷
- 从文件读取的外部输入
- API 接口传入的参数

### 2.2 什么是"污点传播"

污点数据进入程序后，会通过赋值、函数调用、内存拷贝等方式在程序内部流动。追踪这种流动的过程就是"污点传播分析"。

```
【通俗类比】：
把"污点数据"想象成一滴红色墨水。
当它进入一杯清水（程序），墨水会扩散、稀释、转移。
我们需要追踪：这滴红墨水最终流到了哪些杯子（变量/函数），是否被"净化"（安全检查）了。
```

### 2.3 什么是"漏洞挖掘"

在追踪污点传播的过程中，如果发现：

- 污点数据被用作数组索引 → **缓冲溢出风险**
- 污点数据被拼接到命令字符串 → **命令注入风险**
- 污点数据直接写入敏感内存 → **内存破坏风险**
- 污点数据未经校验就传给危险函数 → **任意代码执行风险**

这些就是需要上报的"潜在漏洞"。

### 2.4 工作流程总览（一图看懂）

```
┌──────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  ① 提交任务   │ ──▶ │  ② AI 分析代码    │ ──▶ │  ③ 输出漏洞报告   │
│  指定文件和   │     │  追踪污点传播路径  │     │  结构化结果归档   │
│  入口函数     │     │  递归分析子函数    │     │  可检索可追溯     │
└──────────────┘     └──────────────────┘     └──────────────────┘
       │                      │                        │
       ▼                      ▼                        ▼
   耗时: 秒级             耗时: 分钟~小时级          耗时: 秒级
   人工: 简单配置         人工: 无需干预             人工: 复核即可
```

### 3.2 双角色设计

本服务采用"管办分离"设计，同一个程序按角色不同拆成两组 Pod 运行：

| 角色 | 功能 | 类比 |
|------|------|------|
| **API 节点** | 接收用户请求、管理任务生命周期、返回结果 | 银行柜员：接待客户、处理业务、给出结果 |
| **Worker 节点** | 执行 AI 分析计算、递归追踪污点 | 后台专家：处理复杂分析、产出专业报告 |

**为什么这样设计？**
- API 节点不执行计算，保持轻量，可随时响应请求
- Worker 节点专注计算，资源可弹性伸缩
- 单个 Worker 故障不影响其他任务继续执行

## 4. 执行流程详解

### 4.0 污点源自动识别（前置，常开）

任务允许**不填写污点信息**。当任务没有提供任何外部输入（污点）描述，或只填了 `all`（表示“全部参数都当作污点”）时，系统会在正式分析前先做一次「污点源自动识别」：

```
┌──────────────────────────────────────────────────────────┐
│ 阶段零：污点源自动识别（仅入口函数，单轮）                │
│                                                          │
│  ① 提取入口函数的完整源码（带行号）                       │
│  ② 启动一个 AI 智能体（专用系统提示词、单轮对话、无评审） │
│     把完整函数体交给它，只问一个问题：                    │
│     “这个函数里，哪些数据是来自外部、不可信的输入？”      │
│  ③ AI 返回结构化结果（哪些参数/变量是污点、为什么）       │
│  ④ 把识别出的污点回填为入口任务的输入，接续后续正常流程   │
│                                                          │
│  耗时：通常 30 秒 ~ 2 分钟（取决于函数大小）              │
│  产物：run/sessions/d00-taint-source-id.jsonl（可回放）   │
│  失败兜底：识别不出来则退回“分析全部参数”，不影响任务成败 │
└──────────────────────────────────────────────────────────┘
```

说明：

- 该阶段**常开、无需配置**，仅对入口函数生效；子函数的污点由调用关系自动推导，不重复识别。
- 设计目的：降低使用门槛——用户不必预先人工标注“哪些参数是攻击者可控的”，系统能自行判断。

```
│   │                            │
│   └── [d2] ReadInt (第2层)     │

│                                │
```

## 5. 并行化设计

### 5.1 并行层次概览

本服务有三个层次的并发控制，各司其职：

```
┌─────────────────────────────────────────────────────────────────┐
│  层级一：跨 Pod 并行（Worker Pool）  ← 最粗粒度                  │
│                                                                 │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                      │
│  │ Worker-1 │  │ Worker-2 │  │ Worker-3 │  ... 可弹性扩容       │
│  │ 执行任务A │  │ 执行任务B │  │ 空闲等待 │                      │
│  └──────────┘  └──────────┘  └──────────┘                      │
│                                                                 │
│  控制参数：K8s HPA 自动伸缩 (2~5 个 Worker)                     │
│  协调方式：MySQL 轮询 + 心跳租约                                 │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  层级二：Pod 内函数并行（BFS Worker Pool）  ← 中等粒度            │
│                                                                 │
│  在单个 Pod 内，把需要分析的子函数放入队列                        │
│  ┌──────────────────────────────────────┐                       │
│  │         BFS 分析队列                  │                       │
│  │  ┌─────┐  ┌─────┐  ┌─────┐          │                       │
│  │  │函数B│  │函数C│  │函数D│  ...     │  ← max 4个同时运行    │
│  │  └──┬──┘  └──┬──┘  └──┬──┘          │                       │
│  │     │        │        │              │                       │
│  │     └────────┼────────┘              │                       │
│  │              │                       │                       │
│  │     ThreadPoolExecutor               │                       │
│  │     (并发数 = callee_concurrency)     │                       │
│  └──────────────────────────────────────┘                       │
│                                                                 │
│  控制参数：callee_concurrency (默认4，可配置 1~64)               │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  层级三：漏洞挖掘后台并行（Fork Thread）  ← 最细粒度              │
│                                                                 │
│  每个函数分析完成后，不等子函数结果，立即启动漏洞挖掘              │
│                                                                 │
│  函数A 分析完成                                                   │
│  ├── ★ 立即启动：漏洞挖掘线程 (1~5分钟)                          │
│  │   判断函数A内部是否存在漏洞                                    │
│  └── 同时进行：子函数B、C 加入分析队列                            │
│                                                                 │
│  这样设计的好处：                                                │
│  漏洞挖掘不阻塞后续函数的污点分析，总耗时更短                      │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 子函数调度策略（智能分类）

当 AI 分析完一个函数，发现它调用了一些子函数，并不是全部一股脑并行。系统会先用一个"参数分析器"判断：

| 参数类型 | 调度策略 | 代号 | 原因 | 示例 |
|---------|---------|------|------|------|
| 指针/引用类型 | 顺序执行 | **P0** | 前一个函数的分析结果（校验状态）会影响后一个 | `char *buf`、`int &len` |
| 值类型/const | 并行执行 | **P2** | 各子函数分析互不依赖 | `int size`、`const char *msg` |

```
示例：函数 process(buf, size, msg)
         │         │      │
         │         │      └── msg (const char*) → P2 并行
         │         └── size (int) → P2 并行
         └── buf (char*) → P0 顺序（指针，需要累积校验状态）

结果：
  先顺序执行 buf 相关的子函数链
  同时并行启动 size 和 msg 相关的子函数分析
```

### 5.3 去重机制（避免重复分析）

在实际代码中，同一个函数可能在多处被调用。为了避免浪费计算资源，系统使用多维去重：

```
去重检查点（每个子函数入队前必须通过）：

① 函数名去重
   同一个函数+同一个文件+同一个污点参数 → 只分析一次

② 上下文去重
   同一个函数+同一组外部输入参数+同一组安全校验 → 只分析一次

③ 标准库过滤
   memcpy、malloc、strlen 等已知安全/标准函数 → 直接跳过

④ 无定义过滤
   只有声明没有实现的函数 → 跳过（无法分析函数体）

⑤ 深度限制
   超过最大递归深度 → 截断并标记（防止无限递归）

⑥ 全局缓存
   如果该函数在其他任务中已被分析过，直接从缓存获取摘要
```

## 8. 容错与可靠性设计

### 8.1 AI 调用容错

AI 分析依赖大语言模型 API，可能遇到各种异常。本服务设计了四层重试机制：

```
┌──────────────────────────────────────────────────────────────┐
│  第一层：API 错误重试（网络超时、限流、服务端繁忙）            │
│  - 最多重试 100 次                                           │
│  - 初始等待 30 秒，每次翻倍（30→60→120→240... 上限300秒）     │
│  - 对限流错误，额外等待 30 秒                                 │
└──────────────────────────────────────────────────────────────┘
                          │ 仍然失败
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  第二层：AI 进程崩溃重试                                      │
│  - 最多无限重试（-1）或指定次数                               │
│  - 每次等待 10 秒（指数退避）                                 │
│  - 遇到致命错误（模型不存在、模块缺失）则立即放弃              │
└──────────────────────────────────────────────────────────────┘
                          │ 仍然失败
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  第三层：上下文超限恢复                                       │
│  - AI 对话历史太长导致超限                                    │
│  - 触发自动压缩（compact），保留关键信息                       │
│  - 压缩后重新尝试分析                                         │
└──────────────────────────────────────────────────────────────┘
                          │ 仍然失败
                          ▼
┌──────────────────────────────────────────────────────────────┐
│  第四层：空闲超时恢复                                         │
│  - AI 分析卡住，30分钟无输出                                  │
│  - 自动重启分析进程，最多重试 20 次                           │
└──────────────────────────────────────────────────────────────┘
```

### 8.2 Worker 故障恢复

| 故障场景 | 恢复方式 |
|---------|---------|
| Worker Pod 崩溃 | 租约 300 秒后自动过期，其他 Worker 接管 |
| 任务执行到一半 Worker 挂了 | 新 Worker 获取租约后从头执行（任务幂等设计） |
| NFS 存储暂时不可用 | 文件 I/O 操作有异常处理，不导致崩溃 |
| MySQL 连接断开 | 最多重试 5 次（指数退避），仍失败则任务标记为 error |

### 8.3 数据一致性

```
任务执行期间的数据一致性保证：

① 双写策略：
   执行过程写入临时工作目录 (run/)
   分析完成一次性写入最终输出目录 (output/)
   → 确保不会出现"半成品"被外部读取

② flag 文件机制：
   任务开始：立即写 flag=0
   任务通过：覆盖写 flag=1
   → 外部只需检查 flag 就知道任务是否成功

③ 原子写入：
   所有 JSON 文件先写临时文件，再原子重命名
   → 确保不会读到不完整的文件
```

```
└───────────────────┘  └────────────────┘  └────────────────────┘
```

### 10.2 服务依赖

| AI 模型服务 | AI 分析能力 | 任务执行失败（核心依赖） |

## 附录 A：术语表

| 术语 | 通俗解释 |
|------|---------|
| 污点数据 (Taint) | 来自外部的、不可信的数据，如用户输入、网络数据包 |
| 污点传播 (Taint Propagation) | 污点数据在程序内部的流动和扩散过程 |
| 污点源 (Taint Source) | 污点数据进入程序的位置 |
| 污点汇 (Taint Sink) | 污点数据最终到达的危险操作点 |
| 净化 (Sanitization) | 对污点数据的清洗/校验，如长度检查、类型验证 |
| 跟入点 (Followup) | 需要继续分析的子函数调用 |
| Session | AI 智能体的对话历史记录 |
| Prompt | 发给 AI 的指令和分析要求 |
| Token | AI 的计费单位，约等于1个中文字或0.75个英文单词 |
| BFS (广度优先搜索) | 逐层分析调用链，先分析完当前层所有函数再深入下一层 |
| Pod | Kubernetes 的最小部署单元，一个运行中的容器实例 |
| HPA | 水平自动扩容，根据资源使用量自动增减 Pod 数量 |
